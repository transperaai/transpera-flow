# New client deployment

Each client gets their own deployment: one Vercel project, one Neon database, Google sign-in (Microsoft Entra later). Why: [rework-direction](plans/rework-direction.md) decisions 1, 2, 3 and 7.

Austin follows this with Claude running the commands. `bash scripts/new-client.sh` walks the dashboard clicks one at a time and prints the exact URLs for the client you name. **No key, password or connection string goes into chat or the terminal**: secrets are pasted from one dashboard into another, or generated by Claude and sent to Vercel's API without being printed.

Pick a short name for the client (`acme` below) and the production URL (their domain, or `https://acme-flow.vercel.app` to start).

## 1. Vercel project

1. https://vercel.com/new → team selector → pick your team → **Import** next to `transpera-flow` (if it is missing: **Adjust GitHub App Permissions**).
2. Project Name `acme-flow`. **Root Directory → Edit → `apps/web`**. Framework stays Next.js.
3. Add no variables yet. **Deploy** (the first build may fail on missing settings; that is fine).
4. The region is `syd1`, set by `apps/web/vercel.json`. Nothing to click.
5. Settings → **Git** → Production Branch: `main`.
6. Settings → **Domains**: add the client's domain and follow Vercel's DNS instructions. Skip this while using `*.vercel.app`.
7. Optional preview alias: Settings → Domains → add `acme-flow-next.vercel.app` and assign it to a branch. Preview deployments sign in through it (see section 6).

## 2. Neon database

1. Project → **Storage** → **Create Database** → **Neon** (Serverless Postgres) → Continue.
2. Region **Sydney (aws-ap-southeast-2)**, plan **Free**, name `acme-flow-db`. Turn **Neon Auth** off and **Realtime** off. Create.
3. **Connect project**: tick **Production** and **Preview** (Development is optional). **Custom prefix: `DATABASE`**, so the variable is `DATABASE_URL`. The integration may add other `DATABASE_*` variables; the app reads only `DATABASE_URL`.
4. If it offers a database branch for each preview deployment, leave it **off**. One database per client; previews share it.
5. Settings → Environment Variables: confirm `DATABASE_URL` exists for Production and Preview.

## 3. Apply migrations

`pnpm --filter @transpera-flow/db migrate` applies `compat.sql`, then each migration not yet recorded; a second run applies nothing. `--dry-run` lists what is pending.

**Who runs it:** Claude, from a session that has the client's `DATABASE_URL` (`new-client.sh` runs it only if `DATABASE_URL` is already in the shell, after a yes/no). From a cloud container port 5432 to Neon is blocked, so Claude uses Neon's WebSocket route with the connection string fetched from the Neon API into a private scratch file. Details: [`supabase-notes.md`](supabase-notes.md), "Checked on Neon". Austin never copies the string.

## 4. App login

The owner login bypasses row-level security, so the app's queries run as `authenticator`, which can only become `anon` or `authenticated`.

Claude runs, as the owner, with a generated password:

```bash
bash packages/db/scripts/db-sql.sh -v app_password="$APP_PASSWORD" -f packages/db/scripts/create-app-login.sql
```

then builds `APP_DATABASE_URL` (`DATABASE_URL` with user `authenticator` and that password) and sets it in Vercel (Production and Preview, Sensitive) through the API. Safe to re-run: it resets the password. Without `APP_DATABASE_URL` the app falls back to the owner, which is only acceptable locally.

## 5. Environment variables

Settings → Environment Variables. "Sensitive" variables cannot be read back after saving.

| Variable | What it is | Environments | Sensitive | Who sets it |
|---|---|---|---|---|
| `DATABASE_URL` | Neon owner connection (migrations, Better Auth, sign-in access) | Production, Preview | Set by the Neon integration | Neon integration (section 2) |
| `APP_DATABASE_URL` | `authenticator` connection the app's queries use | Production, Preview | Yes | Claude via API |
| `BETTER_AUTH_SECRET` | Signs sessions; 32+ random characters. Without it (or `DATABASE_URL`) the app runs in demo mode | Production, Preview | Yes | Claude via API, generated, never printed |
| `OAUTH_PROXY_SECRET` | Signs the preview-to-alias sign-in hand-off | Production, Preview | Yes | Claude via API, generated, never printed |
| `PREVIEW_ALIAS_URL` | The stable preview alias, if you made one (for example `https://acme-flow-next.vercel.app`). Only this deployment's own alias is trusted | Production, Preview | No | Claude via API |
| `BETTER_AUTH_URL` | This deployment's own URL. Production: the production URL. Preview: the stable preview alias | Production, Preview (different values) | No | Claude via API (Austin may in the dashboard) |
| `AUTH_PROVIDERS` | `google` (default), or `google,microsoft` | Production, Preview | No | Claude via API |
| `ACCESS_ADMIN_EMAILS` | Comma-separated addresses that always sign in as Owner (Austin) | Production, Preview | No | Claude via API |
| `GOOGLE_CLIENT_ID` | Google OAuth client ID | Production, Preview | No | Austin, dashboard |
| `GOOGLE_CLIENT_SECRET` | Google OAuth client secret | Production, Preview | Yes | Austin, dashboard (paste from Google) |
| `MICROSOFT_CLIENT_ID` | Entra app (client) ID. Only with Microsoft | Production, Preview | No | Austin, dashboard |
| `MICROSOFT_CLIENT_SECRET` | Entra client secret value | Production, Preview | Yes | Austin, dashboard |
| `MICROSOFT_TENANT_ID` | The client's Entra tenant. Required with Microsoft; never `common` | Production, Preview | No | Austin, dashboard |
| `NEXT_PUBLIC_SENTRY_DSN` | Error reporting; nothing is sent without it | Production, Preview | No | Austin, dashboard (optional) |
| `SENTRY_AUTH_TOKEN`, `SENTRY_ORG`, `SENTRY_PROJECT` | Source-map upload at build | Production, Preview | Token: Yes | Austin, dashboard (optional) |

Redeploy after changing variables (Deployments → latest → ⋯ → Redeploy).

## 6. Google OAuth

Use the shared **Transpera Flow** OAuth client (Google Cloud project that holds it → https://console.cloud.google.com/apis/credentials → that client). For each deployment add:

- **Authorised JavaScript origins:** the production URL (`https://acme-flow.vercel.app`), and the preview alias if you made one.
- **Authorised redirect URIs:** `<production URL>/api/auth/callback/google`, and `<preview alias>/api/auth/callback/google`.

Other preview URLs sign in through the alias (Better Auth's OAuth proxy), so they need no URI of their own. Save; it can take a few minutes. Then put the shared client's `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` into the project's variables, pasting straight from Google into Vercel.

**Give the client their own OAuth client instead** when they want their own consent-screen name (the shared one says "Transpera Flow"), or when their Google Workspace policy only allows apps their own admin has approved. Same steps in the client's Google Cloud project: Web application, `openid email profile` only, publishing status **In production**.

## 7. Microsoft Entra (later, when a client asks)

1. In the **client's** tenant (their admin does this, or invites Austin): https://entra.microsoft.com → Identity → Applications → **App registrations** → New registration. Supported account types: **this organizational directory only**. Redirect URI (Web): `<production URL>/api/auth/callback/microsoft`.
2. Copy the **Application (client) ID** and **Directory (tenant) ID** from Overview. Certificates & secrets → New client secret → copy the **Value** at once.
3. In Vercel add `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET` (Sensitive) and `MICROSOFT_TENANT_ID`, pasting straight from Entra.
4. Set `AUTH_PROVIDERS=google,microsoft` (or just `microsoft` to turn Google off). Unknown names are ignored, and an empty list means Google. Redeploy.

`MICROSOFT_TENANT_ID` is required: with Microsoft enabled and no tenant, sign-in throws at startup (`apps/web/src/lib/auth/providers.ts`). "common" would let any Microsoft account reach the access check, so never use it.

## 8. Access list

1. `ACCESS_ADMIN_EMAILS` holds the Owner's address (Austin). It signs in as Owner whatever the rules say.
2. Signed in as the Owner: **Settings → Access → "Who can sign in"**. Add the client's **domains** (anyone with a verified address on them gets the domain's role) and **named emails** (a specific role, overriding the domain's). Roles: **Owner** (everything), **Agency admin** (the client's founder and head of CS: edits, sees pay, manages who can sign in except Owners) and **Viewer** (reads everything but individual pay, edits nothing). Anyone unmatched is refused. Only the Owner can add or remove an Owner rule, or a named email in an Owner's domain.

## 9. First sign-in and smoke test

1. Open the production URL, sign in with the `ACCESS_ADMIN_EMAILS` address (the Owner). Expect the app, not an access-denied page or `/demo`.
2. Settings → Access: add the client's domain and emails.
3. Create or upload a process, run a simulation, reload: it persists (database and app login work).
4. Sign in with an address not on the list: it is refused.
5. Open a preview deployment's URL and sign in: it should bounce through the alias and back.

## 10. Costs and limits

- **Neon Free:** 0.5 GB storage and 100 CU-hours a month per project. Compute scales to zero after 5 minutes idle and resumes on the next request (the first request after idle is slower). https://neon.com/docs/introduction/plans
- **Vercel Hobby forbids commercial use.** Move to **Pro** before selling. One Pro seat can host every client project (rework-direction decision 7). https://vercel.com/docs/limits/fair-use-guidelines
- Neon projects and Vercel projects are per client, so check usage per client, not in total.

## 11. Tearing a client down

Export anything the client wants first. Then, with Austin's explicit yes:

1. Vercel → project → Settings → General → **Delete Project** (removes its variables and domains). Remove the domain's DNS records.
2. Neon: Vercel → Storage → the database → delete it (or console.neon.tech → project → Settings → Delete). This destroys all the client's data and cannot be undone.
3. Google Cloud → the OAuth client → remove that client's origins and redirect URIs. If they had their own OAuth client or Entra app, delete it (the client's admin removes the Entra registration).
